# 大模型解题与映射：从"会抄示例"到"真算"

这一节是整个项目最核心、也最容易翻车的地方。记录真实的设计演进与失败原因。

## 1. 问题定义

输入是一段**随机生成**的应用题 + 一条**映射规则**，例如：

```
使用种子: 997072
------------------------------------------------------------
题目: 每个礼品盒有5个糖果;有软糖、硬糖两种礼品盒;小红想要1个软糖,5个硬糖;
      小明、小刚都想要1个软糖;小玉想要1个软糖,5个硬糖;小兰想要7个硬糖。
      设软糖礼盒数量为x,硬糖礼盒数量为y,计算x、y分别为多少。
映射规则1. "x 代表红色,y 代表蓝色;数值大于等于 3 的去 A 区,其他颜色去 C 区"
```

要求输出机器可解析的一行：

```
[red,2,C;blue,3,A]
```

题意会变（文具盒/衣柜/礼品盒/药箱…），**规则也会变**（三种官方规则，见下），
所以不能写死模板。

## 2. 第一版：一阶段，失败了

最初的做法是一次调用让模型同时"解题 + 套规则 + 输出"。现象：

> 输入一道需要算 x=4、y=1 的题，模型直接返回 `[red,2,C;blue,3,A]`。

排查发现**是我自己的提示词害的**——提示词里为了"教格式"写了示例：

```
规则1『x代表红色,y代表蓝色;数值大于等于3的去A区,其他颜色去C区』
  → x=2,y=3 时输出 [red,2,C;blue,3,A]
```

模型看到输入正好是"规则1"，直接**照抄示例答案**，根本没算题目。
这类"提示词污染"在小模型/低温度下尤其明显。

## 3. 第二版：两阶段 + 去污染

### 3.1 拆分职责

| 阶段 | 输入 | 输出 | 目的 |
|---|---|---|---|
| 阶段一 | 题目正文 | `x=<整数>,y=<整数>` | 只负责算术，强制真算 |
| 阶段二 | 已确定的 x/y + 本次规则 | `[color,count,zone;...]` | 只负责规则翻译 |

拆开的好处：阶段二只剩"查表"难度，模型没有机会用"猜答案"蒙混；
阶段一即使算错，也能用 `x+y=5` 这个题目保证做自动校验。

### 3.2 提示词只教方法，不给答案

阶段一提示词要点（无任何"规则→答案"示例）：

```
1) 找准两种物品名与每容器容量 N；
2) 逐句累加需求（"甲、乙都需要 n 个"要乘人数；"设…为x""有A、B两种…"不计入）；
3) x=ceil(totalX/N)，y=ceil(totalY/N)，且 x,y>=1。
不要过程，只输出一行：x=<整数>,y=<整数>（x+y应为5）
```

### 3.3 自动纠错：x+y≠5 时带约束追问一次

首次结果若 `x+y≠5`，把"你给出 x=2,y=2，但题目保证 x+y=5，请重新逐句累加"拼进对话再问一次。
实测可以把 `x=2,y=2` 纠正为 `x=4,y=1`，且**只多花一次调用，不会无限重试**。

### 3.4 结果

同一道题（x=4, y=1，规则 1）：

```
x=4 → 红色，4 ≥ 3 → A 区
y=1 → 蓝色，1 < 3 → C 区
→ [red,4,A;blue,1,C]
```

与人工计算一致。

## 4. 规则文本的鲁棒提取

出题程序给规则的写法不固定，实测出现过：

```
映射规则: x代表红色,...
1. "x 代表红色,..."          ← 编号 + 引号，且没有"映射规则"前缀
映射规则2. "..."              ← 编号紧贴前缀
```

`extract_mapping_rule()` 的处理顺序：

1. 有 `映射规则` 标记 → 取标记之后；
2. 否则按行切分，找出"同时含颜色词 + (区域 或 映射动词)"的片段；
3. 剥掉编号前缀（`1.` / `2、` / `(1)`）和各类引号（`"` `“` `『`）；
4. 其余部分作为题目正文。

三种官方规则均通过（见 `verification/results/test_task_pipeline.txt` 第 12-15 行）。

## 5. 输出解析：取"最后一个答案"

模型有时会先举例再给答案：

```
比如 [red,2,C;blue,3,A] 只是格式示例。
本题 x=4>=3 所以红色去 A。
答案: [red,4,A;blue,1,C]
```

`parse_plan_text()` 优先取 `答案:` 之后的内容，其次取**最后一个**能解析出条目的方括号片段，
避免被推理过程里的示例带偏。

## 6. 失败处理：宁可报错，不要瞎猜

用户明确要求"只通过大模型解题"。因此：

| 情况 | 行为 |
|---|---|
| 未装 requests / 未设 Key / 网络不通 / 超时 / HTTP 错误 | 打印 `无法连接：原因`，**退出码 3**，不执行搬运 |
| 模型回复里没有 `x=..,y=..` | 报错，不猜 |
| 方案解析失败 | 报错，不猜 |

早期版本会用"本地模板求解"兜底，但那个模板只能覆盖两种题型，遇到随机题会**静默给出错误答案**，
比报错更危险，所以已整体删除。

## 7. Token 优化（调用次数不变）

用户要求"省 token 但不要减少 LLM 调用次数"。做法：

| 项 | 优化前 | 优化后 |
|---|---|---|
| 简单指令 system prompt | ~430 字符 | 268 字符 |
| 工具定义 `TOOLS` | ~2900 字符 | 1636 字符 |
| 阶段一提示词 | ~400 字符 | 161 字符 |
| 阶段二提示词 | ~430 字符 | 178 字符 |
| `max_tokens`（指令/阶段二/阶段一） | 256 / 128 / 1500 | 96 / 48 / 160 |

提示词与工具定义整体精简约 **40%**，调用次数保持：简单指令 1 次、出题 2 次（+ 必要时 1 次追问）。

## 8. 另一个收益：延迟

同一套精简让"放下物块"这类短指令从"超时（10 s）"变成秒级返回——
原因不只是 token，而是提示词里补了一条明确映射：

```
只说"放下/松开/释放物块" → control_gripper(open)
```

此前提示词写着"不要用 control_gripper 拆分搬运流程"，模型遇到"放下物块"会去套
`deliver_cube`（缺 color/id/zone），于是反问或空转。
